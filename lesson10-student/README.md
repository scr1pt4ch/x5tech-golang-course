# Сервис заказов

Небольшой backend-сервис на Go. Через REST API можно создать заказ, посмотреть один заказ или список всех, перевести заказ по статусам и получить историю его изменений.

Заказы хранятся в памяти и пропадают после перезапуска.

## Как запустить

```bash
go mod tidy
go run ./cmd/api
```

Сервер слушает порт `8080`. Другой адрес можно задать переменной окружения: `HTTP_ADDR=:9090 go run ./cmd/api`.

Документация доступна в Swagger UI: <http://localhost:8080/swagger/index.html>.

## API

| Метод | Путь | Что делает | Успех |
|---|---|---|---:|
| GET | `/health` | Проверка, что сервис жив | 200 |
| POST | `/api/v1/orders` | Создать заказ | 201 |
| GET | `/api/v1/orders` | Список заказов | 200 |
| GET | `/api/v1/orders/{id}` | Заказ по id | 200 |
| PATCH | `/api/v1/orders/{id}/status` | Изменить статус | 200 |
| GET | `/api/v1/orders/{id}/history` | История статусов | 200 |

## Бизнес-логика

В заказе должна быть хотя бы одна позиция. У каждой позиции должно быть непустое название, а количество и цена должны быть положительными.

Цены передаются целым числом в копейках. Так не бывает ошибок округления, как с `float`. `total_price` всегда считает сервер. Если сумма не помещается в `int64`, заказ отклоняется, а не сохраняется с отрицательной суммой.

**Статусы**

`completed` и `cancelled` - конечные статусы, из них перейти никуда нельзя. Каждая смена статуса добавляет запись в историю, время пишется в UTC.

Разрешены переходы от `new` к `processing`, `cancelled`.
От `processing` к `completed`, `cancelled`.

## Ошибки

Все ошибки приходят в одном формате:
```json
{"error": "invalid status transition: from new to completed", "code": "INVALID_STATUS_TRANSITION"}
```

| HTTP | `code` | Когда |
|---:|---|---|
| 400 | `INVALID_JSON` | Тело не JSON, в нём лишние поля или мусор после объекта |
| 400 | `INVALID_ORDER` | Заказ не прошёл валидацию |
| 400 | `INVALID_STATUS` | Такого статуса не существует |
| 400 | `INVALID_ID` | id в пути не положительное число |
| 404 | `ORDER_NOT_FOUND` | Заказа нет |
| 404 | `ROUTE_NOT_FOUND` | Неизвестный путь |
| 405 | `METHOD_NOT_ALLOWED` | Метод не поддерживается |
| 409 | `INVALID_STATUS_TRANSITION` | Переход запрещён правилами |
| 500 | `INTERNAL_ERROR` | Что-то пошло не так. Подробности пишутся только в лог |

## Логи

На каждый запрос пишется одна JSON-строка:

```json
{"level":"INFO","msg":"request","method":"POST","path":"/api/v1/orders","status":201,"duration":0.18,"request_id":"2ec2b3a6d4d2dd45"}
```

- `duration` - время обработки запроса в миллисекундах;
- `request_id` берётся из заголовка `X-Request-ID`, если клиент его прислал, иначе генерируется. Он возвращается в ответе, так что по нему легко найти нужный запрос в логах;
- ответы 5xx пишутся с уровнем `ERROR`, чтобы их сразу было видно;
- если обработчик падает с паникой, сервер не останавливается: клиент получает 500, а в лог пишется паника с тем же `request_id`.

## Как устроен проект

```
cmd/api/                     точка входа и общее описание API для Swagger
docs/                        сгенерированная Swagger-документация
internal/order/              модель заказа, ошибки, интерфейс репозитория
internal/repository/memory/  хранилище в памяти
internal/service/            бизнес-логика: валидация, статусы, история
internal/handler/            HTTP: маршруты, обработчики, middleware
```

Слои зависят друг от друга в одну сторону: `handler -> service -> repository`. Сервис получает репозиторий через конструктор как интерфейс, поэтому в тестах его легко подменить фейком, после можно будет расширить до полноценной БД.

## Дополнение

Пока что нет обработки параллельных заказов, т.к. мы их не проходили в рамках курса. После можно будет развернуть в докере и поднять БД, а не хранить заказы в памяти.
